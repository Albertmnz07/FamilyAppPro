# Hexagonal backend architecture and repository layout under `apps/`

The repository groups the two applications under `apps/backend` and `apps/frontend` while keeping build orchestration, compose stacks, hooks, and documentation at the root. Inside `apps/backend` (`albertmnz07.familyapp`), the Spring Boot back-end adopts a strict Hexagonal Architecture divided into three layers enforced by ArchUnit:

- **`domain`** (`model`, `valueobject`, `repository`, `exception`): pure Java with zero framework imports. `Persona`, `Family`, `Membership`, `Invite`, and `AuthToken` are Aggregate Roots that reference one another only through typed ID Value Objects. `Consent` becomes an internal Entity inside the `Membership` aggregate rather than a standalone repository root, enforcing in memory ADR-0001's invariant that accepting a membership grants consent, removing a member revokes it, and consent never exists without a membership. Every rule-bearing property (`Username`, `DniNumber`, `DniPhoto`, `RawPhoto`, `Dni`, `RawPassword`, `PasswordHash`, `FamilyName`, `InviteCode`, `TokenValue`, and typed IDs) is modeled as its own Value Object, and domain failures extend `DomainException`.
- **`application`** (`command`, `query`, `port`): pure Java use-case handlers separated into explicit `*Command`/`*CommandHandler` (mutations over aggregates and repositories) and `*Query`/`*QueryHandler` (returning application read models and `PagedResult<T>`), plus outbound non-repository ports (`PhotoStore`, `PasswordHasher`, `InviteCodeGenerator`, `Clock`). Handlers are injected directly into web controllers with no mediator bus.
- **`infrastructure`** (`persistence`, `storage`, `security`, `web`, `config`): adapts the pure core to Spring and PostgreSQL without changing the external contract or the Flyway `V1`–`V3` schema. Persistence uses dedicated `*JpaEntity` classes, Spring Data repositories (including pessimistic write locking for `InviteRepository.findByCodeForUpdate`), and mappers—persisting the `Membership` aggregate across both the `membership` and `consent` tables. Spring `@Configuration` wires use-case beans and transactions, while `infrastructure.web` preserves every REST endpoint, `@Valid` request check (`validation-failed`), `PageImpl` JSON payload, OpenAPI schema (ADR-0005), and the twelve `ProblemDetail.code` mappings expected by the front-end.

**Considered options:** keeping JPA `@Entity` classes in `domain` or `@Service`/`@Transactional` in `application` was rejected so domain rules and orchestration stay decoupled from persistence and framework lifecycle; keeping `Consent` as a separate Aggregate Root with its own repository was rejected because manual two-repository coordination in services risked drifting membership status from consent state; adding a `CommandBus`/`QueryBus` was rejected as unnecessary indirection.

**Consequences:** this amends the root-level paths recorded in ADR-0006, ADR-0008, and ADR-0009 (`frontend/` → `apps/frontend/`, back-end sources → `apps/backend/`), while preserving ADR-0006's single-artifact production JAR and ADR-0003's existing SQL migrations. In `login` and `redeemInvite`, inputs that fail Value Object format parsing during lookup still surface as `401 unauthorized` and `404 not-found` so front-end error handling remains unchanged.
