# Code formatting tools

Formatting is owned by tooling, not by hand: Spotless runs google-java-format (AOSP style) over `apps/backend` (configured in `apps/backend/pom.xml`) and Prettier runs over `apps/frontend` (configured in `apps/frontend/.prettierrc.json`, excluding generated `apps/frontend/src/api/schema.d.ts`; paths amended by ADR-0010). From the repository root, `.githooks/pre-commit` formats the staged Java files under `apps/backend/` and TypeScript/TSX/CSS files under `apps/frontend/src/` and re-stages them, so a commit cannot land unformatted, while `.githooks/pre-push` and `.github/workflows/format.yml` re-verify the whole tree with the strict checks (`make format-check`). The front-end keeps the conventions the repository already used (semicolons, double quotes, 100-column width); one isolated commit reformats the whole repository so the baseline is uniform rather than ratcheted.

**Considered options:** oxfmt, the Oxc formatter that would have matched the oxlint already in use, was rejected because it is not idempotent — a single pass over a chained call carrying an object argument is rewritten again by the next pass, so `oxfmt --check` fails on the file oxfmt has just written (oxc-project/oxc#28916), which breaks the commit-then-verify loop. Spotless `ratchetFrom` was rejected because it leaves two styles side by side instead of one, and palantir-java-format (120 columns) in favour of the 100-column google-java-format AOSP.

**Consequences:** agents must not format by hand — they run `make format` (which runs Spotless in `apps/backend` and Prettier in `apps/frontend`) and let the commit hook be the source of truth for style. A fresh clone must run `make setup` once to enable `.githooks/`, backed up on pull requests and pushes to `main` by CI running `make format-check`.
