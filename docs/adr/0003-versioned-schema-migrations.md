# Versioned schema migrations

The schema is owned by the ordered SQL migrations in `src/main/resources/db/migration`, applied by Flyway on startup. Hibernate no longer changes the schema: it only validates the migrated one against the entities (`spring.jpa.hibernate.ddl-auto=validate`), so a migration that drifts from the entities fails the build and the tests.

We chose this over letting Hibernate update the schema (`ddl-auto=update`): Hibernate's changes are unreviewed, unversioned and unrepeatable, so a schema change cannot be reasoned about, replayed on a fresh database, or rolled back. We chose Flyway over Liquibase because its plain-SQL migrations match the way the schema is already written down. `V1` is the schema that `ddl-auto=update` produced, including the legacy DNI photo bytea columns; `V2` drops them after TN-08 moved photos to object storage. A database that existed before Flyway was adopted is baselined at V1 — the version that matches that legacy schema — so it skips `V1` and receives `V2` and every later migration, while a fresh database replays all of them.
